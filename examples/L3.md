# L3 示例｜生产订单状态修改

## 场景

生产系统中，某订单在满足特定条件后会自动进入下一业务状态。当前规则存在 Bug，可能导致真实订单被错误推进。

## GPT 判断

```text
RISK=L3
```

原因：

- 涉及真实生产订单状态
- 自动写入
- 错误可能产生业务损失
- 需要证明源码正确、Runtime 正确、最终业务结果正确

## Codex Task

```text
CLAIM:
修复订单自动推进规则，使只有满足既定条件的订单进入 READY 状态，并保持其他订单状态不变。

CONTEXT:
- 已确认错误发生在 eligibility 判断。
- 当前逻辑会把一类不满足条件的订单错误推进。
- 生产写入属于高风险操作。

RISK:
L3

CHANGED_SURFACE:
- eligibility 判断逻辑
- 对应状态转换测试
- 必要生产者 / 消费者 Contract 验证

ACCEPTANCE:
1. 满足条件的订单可进入 READY。
2. 不满足条件的订单保持原状态。
3. 公共订单状态 Contract 不变。
4. 固定 Review Snapshot 通过 GPT Review。
5. 正式 Runtime 验证真实行为正确。
6. 必要时通过真实业务结果回读证明 Outcome。

CONSTRAINTS:
- 未获授权不得批量修改生产订单。
- 不修改其他订单状态机规则。
- 不进行不可逆数据修复。
```

## Codex 执行

```text
真实环境调查
→ 最小源码修改
→ T0
→ T1
→ 必要 T2/T3
→ Review Snapshot
→ 必要 Clean Reproduction
→ Push Review Branch
→ Handoff
```

## GPT Delta Review

GPT 实际读取固定 SHA 与 Diff，重点确认：

- 状态机边界是否正确
- 是否存在新增误写入路径
- 测试是否覆盖正例、反例和边界条件
- 生产者 / 消费者 Contract 是否兼容
- Clean Reproduction 是否存在 Source Escape

只有固定 `REVIEW_HEAD` 通过后：

```text
GPT_REVIEW=ACCEPTED
```

才允许进入下一阶段。

## Integration

按项目自己的 Integration Contract：

```text
最新 canonical
→ clean
→ 安全集成固定 Review Head
→ 不允许 force push
```

## Runtime Acceptance

不能只证明：

```text
服务启动成功
HTTP 200
脚本 exit 0
```

必须验证真实状态转换行为。

例如使用安全测试订单或明确获授权的生产验证样本：

```text
满足条件样本
→ READY

不满足条件样本
→ 状态不变
```

若正式生产写入未获授权，应停止在可安全证明的边界，并明确 `BLOCKED` 或等待授权，不得偷偷执行。

## Outcome Acceptance

如果 Claim 的最终结果依赖业务事实，还需要真实回读：

```text
订单最终状态正确
无额外订单被错误推进
相关下游结果符合预期
```

## 最终关系

```text
Source Test PASS
≠ GPT Review ACCEPTED

GPT Review ACCEPTED
≠ Runtime Accepted

Runtime Accepted
≠ Outcome Accepted
```

L3 的目标不是流程最多，而是：

> **对可能造成明显业务损失的修改，提供足以证明最终结果的完整证据链。**
